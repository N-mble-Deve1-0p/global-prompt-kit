# 开源方案调研：先调研，后动手

## 铁律
- 本技能全程不写实现代码，只调研、评估、出方案。
- 结尾必须停下，等用户确认后才进入开发。
- 必须联网查看真实仓库。环境不能联网时，明确告诉用户：只能列出训练数据中记得的候选，维护状态和许可证全部标为"未核实"。
- 能用 git 或 GitHub CLI 时，直接克隆或查询仓库来核实提交记录、许可证和目录结构，比只读网页可靠。

## 第 0 步：补全需求
缺什么问什么，一次最多问 4 个。用户已经说清楚的不要重复问。

必须知道：
1. 要做的东西是什么，核心要解决的 1–3 个问题
2. 使用场景：自用 / 团队内部 / 对外商用（决定许可证风险）
3. 部署环境：本地、单台 VPS、K8s、Serverless、纯前端等
4. 技术栈偏好或硬约束（语言、数据库、必须对接的系统）

可选：规模预期、预算、上线时间。

信息足够就直接开始，并把自己做的假设写在报告开头。

## 第 1 步：广撒网找候选
至少用 3 种来源：
- GitHub 搜索（关键词 + topic，按 stars 和最近更新分别排序）
- awesome-* 列表
- alternativeto.net、"open source alternative to X" 类讨论
- Hacker News、Reddit 上的真实使用反馈

先列 8–15 个候选，再筛到 3–5 个深入评估。

## 第 2 步：逐个核实
看仓库本身，不只看 README。每个候选都要拿到具体数据：

| 维度 | 怎么查 | 判定参考 |
|---|---|---|
| 维护状态 | 最近一次提交、最近一次 release、近 6 个月提交频率 | 6 个月内有提交且有 release 为"活跃"；超过 12 个月无动静为"停滞" |
| 社区健康 | 近期 issue/PR 的响应速度、活跃贡献者数量 | 只有一个维护者的要标注风险 |
| 许可证 | LICENSE 文件 | MIT/Apache 最宽松；GPL 注意衍生作品；AGPL 用于对外 SaaS 需明确警告；没有许可证等于不能用 |
| 部署难度 | 有无 Docker / docker-compose、依赖组件数量、文档完整度 | 1 分（一条命令跑起来）到 5 分（多组件、大量配置） |
| 功能匹配 | 对照第 0 步的核心需求逐条核对 | 标注：现成可用 / 需改造 / 缺失 |
| 可改性 | 代码结构、插件/扩展机制、技术栈是否与用户一致 | 文字说明 |

所有数据注明查询日期和来源链接。查不到就写"未知"，不要猜。

## 第 3 步：决策（三选一）
- **直接用**：核心需求覆盖 ≥80%，活跃维护，部署难度 ≤2，许可证无冲突
- **基于现有项目改**：有项目覆盖了主干，缺的部分能通过插件或少量改动补上
- **自己开发**：没有合适候选，或改造成本接近重写，或许可证不允许

以上阈值是默认参考。用户场景特殊时（比如只有一个核心需求但极其关键）按实际判断，并说明为什么偏离默认。

## 第 4 步：最简 MVP 方案
- 只包含解决核心问题必需的功能，其余列入"之后再做"
- 写清楚：用哪个项目/组件、要改或新写哪几块、部署方式、预估工作量（按人天）
- 列出最大的 2–3 个风险和应对办法

## 输出格式
1. 一句话结论（直接用 / 改 / 自研 + 推荐项目）
2. 需求摘要与假设
3. 候选对比表（3–5 个）
4. 决策理由
5. MVP 方案
6. 风险
7. 来源链接

结尾固定一句：「以上方案确认后我再开始动手，需要调整请告诉我。」
